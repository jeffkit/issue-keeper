# 阻塞性系统缺陷：直修流程（值守 Agent 第一职责）

> **授权来源**：jeffkit 2026-10-10 拍板——
> 「系统的阻塞性问题，优先是你（看守 Agent）来解决……不要傻傻像今天一样加到 issue 里等系统自己解决，
> 如果是这样的话，看守的 agent 价值就太小了。」
> 「有问题就要趁早解决，不要等。」

## 1. 什么时候必须**当场修**（而不是立单排队）

命中任意一条 ⇒ 走本流程：

| 特征 | 判据 |
|---|---|
| **在放血** | 正在持续烧配额 / 沙箱实例小时 / 磁盘 / 槽位；或产出长期为 0 |
| **系统性** | 不是单个 issue 倒霉，而是**机制**让同类反复发生（看门狗误报、重试不生效、队列被打穿） |
| **我能修** | 代码 / 配置 / 看门狗 / flow 在我手上，**不需要业务拍板** |

反例（这些才立 issue 或发 HITL）：单个 issue 的业务修复、需要拍板的成本/并发/档位、A/B 班 automation。

**立 issue ≠ 交付**。issue 只是留痕；交付是「**代码改了 + 验证过 + 已提交 + 观察到了效果**」。

## 2. 直修五步（顺序不可省）

### ① 读实现（不许先下结论）
定位到**具体行号**，读懂控制流。看门狗类缺陷尤其先确认：这个判据的输入到底是什么时间段。

### ② 造**可复现**实验（本流程的核心）
在动代码之前，先造一个能**定量**证明机制的实验。优先级：
1. **静态快照定量**（最快、最硬）：扫全库看**值分布 + TTL 形态**。
   实战：`--scan --pattern "*noderetry*"` → **74 个键全为 1**、TTL 各不相同
   ⇒ 每键只 `INCR` 过一次、没有被反复 `DEL` ⇒ **一条命令推翻「被反复清零」的假设**。
2. **日志定量**：按时间窗聚合错误文本、按执行归属 `uniq -c`（别只看行数）。
3. **单测复现**：用 `fakeredis` + `MagicMock` 把生产调用形态写成测试。
4. 实时跟踪 `MONITOR` / keyspace 通知——**注意**：命令要 `timeout` 包裹，且事后要确认采样窗口内确有事件。

### ③ 改（最小、外科式）
- 改**判据/机制**，不是改阈值掩盖。
- 阈值调参只当**临时止血**，且必须在轮报里标「阈值掩盖、非修复」（例：`stall_min` 30→130）。

### ④ **反证**（唯一验收，缺这步不算修完）
把修复**退回旧行为**，跑同一实验/测试，**必须变红**。不红 ⇒ 你根本没修到点子上。
- 实战教训：2026-10-10 我按错误假设改了 `flow_worker.py` 的清零条件，写好测试全绿；
  **退回旧代码测试仍然全绿** ⇒ 立刻判定修复无效并**撤回**（`git checkout` + 删测试），
  没有把未证实的东西推进主干。
- 撤回来的东西可以再上，**没验证过的东西不许上**。

### ⑤ 提交 + 观察 + 留痕
- commit message 写**为什么**（含证据）；相关 issue 补评论更正机制。
- 提交后必须**观察到效果**（下一轮探针/轮报确认指标变化），否则视为未完成。

## 4. 与「能力矩阵」的关系

本流程**不改变**能力矩阵的红线：
- 仍然**必须发 HITL** 的：重启任何服务、改并发/模型档/基础设施、任何成本或对外承诺、重大拍板、关单。
- 直修的边界 = **我自己仓库里的代码 / 我自己的 flow 与看门狗配置 / 值守内核**。
- 缺依赖时：**先问人**，不要为了「趁早解决」去动基础设施。

## 5. 一句话总结

**发现阻塞性系统问题 → 当场读代码取证 → 造实验 → 修 → 反证 → 提交 → 观察。**
立 issue 只是留痕，**不是**解决方案；把问题丢进队列等系统自己修，是值守 Agent 的失职。

## 6. 部署检查项：**「重启」≠「代码生效」**（2026-10-10 实证）

多执行点架构下（Mac 本机 + VM tcg1 + AGS 沙箱），**每个执行点的代码来源可能不同**：

| 执行点 | 代码来源 | 改代码后如何生效 |
|---|---|---|
| Mac `plaita-worker-mac` | 与开发共享同一工作区 `/Users/kong/projects/infra4agent/plaita` | 提交后**重启即生效** |
| VM `plaita-flow-worker@tcg1` | **VM 自己的 checkout**（含本地未推提交） | **必须先把代码同步过去**，再重启 |
| AGS 沙箱 | 由 VM 侧 checkout 打包/sync_in | 跟随 VM |

**踩坑实录**：修好 #73 后我推了 main 并重启两 worker，以为完事；
复核时 `ssh tcloud_gz 'grep -c NodeFailureTerminalizedError .../flow_worker.py'` = **0**
——VM 仓 HEAD 停在另一个提交（`73f1adc`，本地另有 3 个未推提交），
**重启后 VM 侧仍跑旧逻辑**。只重启不同步 = 白重启。

**标准动作（重启任何人之前）**：
1. 在**每个**执行点上确认代码来源：`git -C <path> log --oneline -1` 与
   `git status --porcelain`（**先看有没有他人/本地未推提交，别覆盖**）；
2. 用**符号级检查**确认目标修复在位，而不是看提交时间：
   `grep -c "<新增的类名/函数名>" <file>`（=0 就是没生效）；
3. 若目标点分叉（有未推提交）：**cherry-pick 目标提交**，不要 `pull --rebase` 硬并；
4. 在**该执行点**跑一次相关测试（`~/.venvs/issuekeeper/bin/python -m pytest ...`），绿了再重启；
5. 重启后按**启动时刻**切分日志验证（`awk "/<启动时刻>/,0"`），别把旧进程临终日志算进新代码。

**归因纪律**：验证时先确认日志行的**时间戳相对新进程启动时刻**的位置——
我一度把 00:49:30 的旧签名当成「修复无效」，而新 worker 是 00:49:31 启动的。

## 7. 写方案前的**可达性三连**（2026-10-10 三版方案连续被否的教训）

> 三次被否全是同一个病：**读了几处代码就下机制结论，没把数据流走通。**
> v1 没查 `raise` 有没有 `from exc`（前提被证伪）；v2 没查 `provider` 在 worker 层
> 是否存在（修复不可实现）；v3 没查判死依据是「当前值还是峰值」、没查触发路径
> 是否可达（证明的是自锁场景）。

**任何机制结论或修复方案落地前，必须先把这条数据流的三个点 grep 出来：**

| 检查 | 怎么查 | 反面案例 |
|---|---|---|
| **① 写入点** | `grep -n "<键名>\|_record_"` 找出**所有** INCR/SET，确认**触发条件分支** | v1 以为没写，实际在写 |
| **② 读取点** | 找出**所有**消费处，确认判据用的是**当前值**还是**峰值**、是**谁**在读 | v3 用峰值论证当前值语义 |
| **③ 可达性** | 问「这个修复动作**在故障状态下还跑得到吗**？」画出调用链，确认没有前置拦截 | v3 的 HALF 放在自锁之外，永不触发 |

**④ 触发规模**：`redis-cli --scan --pattern "*<键名>*" | wc -l` —— **先确认问题真的在发生**。
`nofail` 键数 = 0（从未触发）却写了三版修复方案；`noderetry` 544 个键才是真实战场。

**判据**：如果三个点没查全，**不要写方案**。宁可先花 10 分钟 grep，也不要产出被否的方案。
