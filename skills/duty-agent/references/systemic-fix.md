# 阻塞性系统缺陷：直修流程（值守 Agent 第一职责）

> **授权来源**：jeffkit 2026-10-10 拍板——
> 「系统的阻塞性问题，优先是你（看守 Agent）来解决……不要傻傻像今天一样加到 issue 里等系统自己解决，
> 如果是这样的话，看守的 agent 价值就太小了。」
> 「有问题就要趁早解决，不要等。」

## 1. 什么时候必须**当场修**（而不是立单排队）

命中任意一条 ⇒ 走本流程：

| 特征 | 判据 |
|---|---|
| **在放血** | 正在持续烧配额 / 沙箱实例小时 / 磁盘 / 槽位；或产出长期为 0 |
| **系统性** | 不是单个 issue 倒霉，而是**机制**让同类反复发生（看门狗误报、重试不生效、队列被打穿） |
| **我能修** | 代码 / 配置 / 看门狗 / flow 在我手上，**不需要业务拍板** |

反例（这些才立 issue 或发 HITL）：单个 issue 的业务修复、需要拍板的成本/并发/档位、A/B 班 automation。

**立 issue ≠ 交付**。issue 只是留痕；交付是「**代码改了 + 验证过 + 已提交 + 观察到了效果**」。

## 2. 直修五步（顺序不可省）

### ① 读实现（不许先下结论）
定位到**具体行号**，读懂控制流。看门狗类缺陷尤其先确认：这个判据的输入到底是什么时间段。

### ② 造**可复现**实验（本流程的核心）
在动代码之前，先造一个能**定量**证明机制的实验。优先级：
1. **静态快照定量**（最快、最硬）：扫全库看**值分布 + TTL 形态**。
   实战：`--scan --pattern "*noderetry*"` → **74 个键全为 1**、TTL 各不相同
   ⇒ 每键只 `INCR` 过一次、没有被反复 `DEL` ⇒ **一条命令推翻「被反复清零」的假设**。
2. **日志定量**：按时间窗聚合错误文本、按执行归属 `uniq -c`（别只看行数）。
3. **单测复现**：用 `fakeredis` + `MagicMock` 把生产调用形态写成测试。
4. 实时跟踪 `MONITOR` / keyspace 通知——**注意**：命令要 `timeout` 包裹，且事后要确认采样窗口内确有事件。

### ③ 改（最小、外科式）
- 改**判据/机制**，不是改阈值掩盖。
- 阈值调参只当**临时止血**，且必须在轮报里标「阈值掩盖、非修复」（例：`stall_min` 30→130）。

### ④ **反证**（唯一验收，缺这步不算修完）
把修复**退回旧行为**，跑同一实验/测试，**必须变红**。不红 ⇒ 你根本没修到点子上。
- 实战教训：2026-10-10 我按错误假设改了 `flow_worker.py` 的清零条件，写好测试全绿；
  **退回旧代码测试仍然全绿** ⇒ 立刻判定修复无效并**撤回**（`git checkout` + 删测试），
  没有把未证实的东西推进主干。
- 撤回来的东西可以再上，**没验证过的东西不许上**。

### ⑤ 提交 + 观察 + 留痕
- commit message 写**为什么**（含证据）；相关 issue 补评论更正机制。
- 提交后必须**观察到效果**（下一轮探针/轮报确认指标变化），否则视为未完成。

## 3. 本体系已验证的「高危区」清单（优先查这些）

| 区域 | 已知缺陷 | 状态 |
|---|---|---|
| 节点重试预算（`flow_worker.py`） | `INCR` 被 `_is_retryable_node_failure` 短路 ⇒ 确定性失败**永不耗尽预算**，靠消息层无限重投 | 机制已实证（#73 正文需更正） |
| 沙箱 sync_in（plaita#120） | 宿主 main 直推后沙箱基线脱节，3-way merge 缺 blob ⇒ 必然失败、不自愈、8 次/分空转 | 已实证；换新沙箱即自愈 |
| 看门狗判据 | inflight-watch「在途时长当终态滞后」（已修 1.1.0）；sandbox-watch「无节点更新当无进展」（#23）；「paused 当浪费」（已修 `98fc22f`） | 部分已修 |
| 探针口径（`duty_probe.py`） | 「落地」只按派发窗口统计 ⇒ 老 run 刚落地不算数（假 DEGRADED，已修 `07fa831`）；「重投风暴」信号（`4156f04`） | 已修 |
| 沙箱成本口径 | `sandbox-watch` 只看「孤儿 / paused 空闲」，**看不到「重投风暴期间实例持续占位」**（实测风暴窗口烧 5.66 实例小时） | 建议加 `thrash_hours`（与 `waste_hours` 并列、不混算） |

## 4. 与「能力矩阵」的关系

本流程**不改变**能力矩阵的红线：
- 仍然**必须发 HITL** 的：重启任何服务、改并发/模型档/基础设施、任何成本或对外承诺、重大拍板、关单。
- 直修的边界 = **我自己仓库里的代码 / 我自己的 flow 与看门狗配置 / 值守内核**。
- 缺依赖时：**先问人**，不要为了「趁早解决」去动基础设施。

## 5. 一句话总结

**发现阻塞性系统问题 → 当场读代码取证 → 造实验 → 修 → 反证 → 提交 → 观察。**
立 issue 只是留痕，**不是**解决方案；把问题丢进队列等系统自己修，是值守 Agent 的失职。
