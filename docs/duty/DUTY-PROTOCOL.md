# DUTY-PROTOCOL —— 值守协同协议（v0 草案）

> 状态：**草案**，待 jeffkit 逐条过（特别是 §5 能力矩阵的档位归属）。
> 作者：主控会话 + jeffkit 2026-10-08 讨论 | 归属：issue-keeper 仓（业务侧）
> 关联：`.zcode/skills/*`（旧 zcode 值守形态）、`issue-keeper/flows/keeper_watch_flow.py`（B 值守 flow）、
> `~/.issue-keeper/pipeline/controller/playbook.md`（现役事实来源，本协议成熟后取代）

## 0. 这份协议解决什么

现役值守协同（主控 + A 验收班 + B 接单班）的事实来源是**本机文件**：
`~/.issue-keeper/pipeline/controller/{playbook,roster,directives,rounds.log,handoffs/}`。
调度是 zcode 的 `~/.zcode/v2/tasks-index.sqlite`，唤醒靠**绑定会话 id**。

三个后果（按严重度）：

1. **状态机住在本机** —— 换台机器协同即失效；无版本、无 schema、无测试。
2. **权限是散文** —— 红线写在提示词里，是**建议**而非约束；越权不可审计、不可测试。
   实证：2026-10-08 夜 B 班回收 `~/recursive-src/target` 连带打断 `~/.local/bin/recursive`
   软链，致 VM 全 impl 失败 13 分钟 —— 红线里**已经写了**要查软链，仍发生。
3. **人肉调度** —— 主控每小时的判活/催办/换班全是可规则化的动作，却由一个长会话承担。

**本协议的目标**：把上述三样迁到**结构化、可校验、可测试**的形态，
markdown 降级为**渲染产物**（人读），不再是事实来源（机器读）。

## 1. 分层与边界（不可越）

```
┌────────────────────────────────────────────────────────┐
│ plaita / plaita-console —— 编排内核                      │
│ 只负责「图 + 挂起恢复 + 事件」。不加 duty、不加业务资源。 │
│ 依据：ADR-2026-08-27 决策 3（业务语义不进编排框架）      │
└────────────────────────────────────────────────────────┘
        ▲ 被调用（flow 定义 + execution）
        │
┌────────────────────────────────────────────────────────┐
│ duty —— 业务侧（本协议范围；落 issue-keeper 仓）         │
│ 值班状态机 / 指令板 / 人机边界 / 投影                     │
└────────────────────────────────────────────────────────┘
        ▲                    ▲                    ▲
   值守 flow 的         跨机参与者           GitHub 投影
   CODE 节点调用        （HTTP）            （信箱 / 公告）
```

**duty 与 keeper 的关系**：不是寄宿，是**同类归并**——两者都处在 flow 之外、
持有跨轮状态、管边界与出害口。

**keeper 不退役**。flow 拿走的是**决策与执行**（`_dispatch_*` / `_reap_*` / gate 调度 /
agent 编排）；结构性留下的三类，恰是 duty 最需要贴着的：

| 留下的 | 内容 | 为什么迁不进 flow |
|---|---|---|
| **状态存储** | `state.json`（`ItemState` 全字段）、`internal.db`（`projects` 表=单一配置源）、`runs.jsonl`、`pipeline/<repo>-<n>/` | 跨轮次长期记忆；flow execution 是一次性的 |
| **出害口 / 安全边界** | `screener`（注入过滤）、`reply`（消毒+礼仪化）、agent 子进程降权（env 白名单、独立低权限 token） | 必须在 flow **之外**；flow 自身即被 sandbox 者 |
| **reaper** | 判终态、跨渠道读回校验、连击判定、WIP 快照、看板回写、退避重派 | 监督者不能住在被监督者里面 |

## 2. 角色

| 角色 | 职责 | 节拍 |
|---|---|---|
| `controller`（主控/节奏官） | 转达 / 配速 / 轮换 / 汇总 / 应急；**不替值守做业务判断** | 1h `:50` |
| `A`（验收侧） | 代码级验收：读完整 diff 逐点核对、跑测试、回评/关单、提报 | 2h `:00` |
| `B`（接单侧） | keeper 派发健康、磁盘守卫、卡单 reopen、fleet/队列运维 | 2h `:40`（flow 化后） |
| `sandbox`（旁支） | 沙箱实例巡检 | 30min |
| `external`（**非值守**） | 外部验收方：只能访问 GitHub，提 issue / 收结论 | 事件驱动 |

`external` **不是黑板用户**——它要的是**信箱**（提需求、收结果），不是状态机。
它的通道已存在（keeper → 内核 → 回评），不需新增 HTTP 面，也因此 **duty 无需暴露公网**。

### 2.1 主控的定位：**事件驱动的仲裁器**，不是定时巡检器（2026-10-08 定）

**问题**：A/B 都 one-shot 化后，主控还需要吗？职责是什么？
**答案**：需要，但职责缩一半——**缩掉的正是现在烧 token 最多的那半**。

现役主控 61 轮的实际动作可分五类，flow 化后三类自动消失：

| 现役动作 | 频率 | 迁移后 |
|---|---|---|
| **A. 判活/巡检** | 每轮 | **消失**——现在要判活是因为调度绑会话（会话会失联）；flow 化后看 execution 状态即可，是查询不是巡检 |
| **B. 指令催办** | 少数 | **规则化**——`directives.max_rounds_unacked` + 一个 CODE 节点判定 |
| **C. 换班执行** | 每班次 | **整个消失**——每轮本就是新 execution，无"会话"要换 |
| **D. 汇总/答问** | jeffkit 触发 | **保留**——渲染跨班视图 |
| **E. 拍板落地** | jeffkit 触发 | **保留**——升级路由 + 拍板回灌 |

**留下的两件事，都不是"定时巡检"**：

**① 跨班次仲裁——它是唯一看到全局的角色。**
A 只看验收队列、B 只看派发/磁盘，而某些判断天然需要同时看两边：

- 「A 说在途 6 个全僵尸」+「B 说 17:09 恢复」→ 合起来才有「17:10 注入 resume」这个决策（2026-10-08 真实发生）
- 「A 降频 2h」+「B-flow 2h」→ **节拍盲区**（17:09-17:40 落在 A 盲区），A 班自己在 handoff §五 指出"需主控注入"
- P0 广播（D-0027 `targets: [both]`）——两班遵守同一套禁令

**② 升级路由——它是唯一有权打扰 jeffkit 的角色。**
必须独立于 A/B：不能让 A 自己决定"要不要升级"（可能已越权而不自知），
也需要对两班同时升级做去重与排序。

**触发模型（两形态，分场景使用）**：

| 形态 | 机制 | 适用场景 | 延迟容忍 |
|---|---|---|---|
| **形态二（起步）** | 低频 cron（30min）→ 读内核 → 判定 → **有则处理，无则立即结束**（不写简报、不烧 token） | 掉班检测、escalate 堆积、指令超时、跨班冲突 | 高（班次是小时级） |
| **形态一** | `EventNode` 挂起 + `subscription_timeout` → 事件到达 resume / 超时走看门狗路径 | **人在环审批**（jeffkit 在等，必须实时） | 必须实时 |

> **形态二起步的理由**：它对 A/B **零改造**（A/B 只管往内核写结构化字段，主控读即可）。
> 且因字段是机器可判的，判定成本≈一次 CPU 比较，不是"LLM 读文件"。
> 实证：2026-10-08 P0 事件（15:40 出事 → 15:51 定时轮处置）**定时轮并未迟到**。
>
> **形态一的真正用武之地是人在环审批**——`EventNode` 的 `correlation_id=execution_id`
> 语义（"等一个与我相关的事件"）与"等 jeffkit 点 resume"完美匹配，
> `subscription_timeout` 正好实现"超时=拒绝"。

**看门狗模式**（主控 cron 的唯一职责）：

```
主控 cron（30min）
  → 只做一件事：检查 A/B 的 state.last_round_at 是否超期
  → 超期 → 触发仲裁/降级链
  → 未超期 → 什么都不做

主控事件驱动（随时，经 Redis 通知）
  → escalate / 冲突 / 人在环审批 → 触发
  → 这才产生简报和升级
```

> **对称性**：主控盯着 A/B 的 `last_round_at`——一个**结构化字段**。
> 这只有在 duty 内核建立之后才成立。**这就是主控 flow 必须建立在 duty 之上、
> 而不是独立存在的原因。**

**权力边界**：`close_issue` / `reopen_issue` / `cancel_execution` 对 controller
一律 `forbidden`（严格按"不替值守做业务判断"）。
**理由**：仲裁者的权力边界越清晰，它越不容易变成第二个单点——
2026-10-07 已实证主控自己会失联（automation 派发全败 ~5h）。

## 3. 轮次生命周期

```
schedule(cron) → enqueue → worker 取 execution
  ① 开机：读 duty 内核（roster 认班 + 上轮 handoff + issued 指令 + 自检探针）
  ② 执行：职责动作（受 §5 档位约束）
  ③ 收尾：写轮报 + 指令回执 + 新 handoff + 投影（GitHub / console / 快照）
```

**无状态 execution**：flow 每次执行都是新实例，全部跨轮上下文来自 duty 内核。
这是"换班"退化为"更新 roster 世代"的前提——不再需要 `rotate_shift.sh` 那套
（建会话 → 备份 sqlite → 直插 `target_task_id` → 回读 → 留痕）。

## 4. 数据模型（四份 Schema）

四份 JSON Schema 见同目录 `schema/`。**强校验分层**：

| 写入者 | 校验强度 | 失败时 |
|---|---|---|
| CODE 节点（程序产出） | 强校验 + 事务，不合法直接抛 | 节点失败（真 bug，应炸） |
| AGENTRUN（LLM 产出） | 强校验 + **一次自动修复回合**（schema 错误回灌）→ 仍不合法则**降级存原文 + 告警** | 轮次继续，告警进健康行 |

> 第二条是关键：**不能让 LLM 的格式抖动变成值班停摆**。散文时代"永远写得进去"
> 这个韧性要保留，但用**告警**把静默容忍变成显式债务。

| Schema | 内容 | 取代 |
|---|---|---|
| `roster.schema.json` | 当班/后备/世代/角色/能力开关 | `roster.md` |
| `state.schema.json` | 轮次 cursor + 结构化轮报（在途/磁盘/异常/动作） | `rounds.log` |
| `directives.schema.json` | 指令 `issued→acked→done/failed/expired` + target + 回执 | `directives.md` |
| `handoff.schema.json` | 结构化交接（在途清单/待办/观察项/口径） | `*-handoff-*.md` |

### 4.1 存储形态（2026-10-08 定）

**文件为准 + Redis 只做通知**（三方确认）：

| 层 | 载体 | 作用 | 失效后果 |
|---|---|---|---|
| **事实来源** | `~/.issue-keeper/duty/*.json` + 现有 `state.py`（`_state_lock` flock + `os.replace` 原子写 + `save_state_merged` 三方合并） | 全部状态 | **不可失**（这是权威） |
| **通知** | Redis pub/sub（只传"某班写了新 state"信号） | 加速器：让主控能即时被唤醒 | 退化为低频 cron 轮询，**无损失** |

```
~/.issue-keeper/duty/
├── roster.json              # 值班表 + 能力矩阵（GATE 的输入）
├── state-{A,B,controller}.json   # 按角色分文件——减少写冲突
├── directives.json          # 指令板
└── handoffs/
    └── {A,B}-<ts>.json      # 滚动交接，保留最近 N 份
```

**为什么不用纯 Redis**：B 班的核心职责是磁盘守卫，**VM 挂了 Redis 就没了**——
恰恰在最需要状态时不可读。文件在本机，Redis 只做加速，丢了降级不丢数据。

**为什么不用纯文件**：文件没有 event bus，A/B 写完后无法 publish，
主控就只能轮询（形态二）。引入 Redis 通知后，紧急事件（人在环审批）才可能实时。

**分文件不分工具**：复用的是 `state.py` 那套"长轮次 + 中途人工介入"的**并发语义**
（`save_state_merged` 的逐字段 diff + `_REOPEN_OWNED_FIELDS` 人工优先），而非数据本身。

### 4.2 保留策略

| 内容 | 保留 | 理由 |
|---|---|---|
| `roster.json` / `directives.json` | 全量 | 需追溯历史决策 |
| `state-*.json` | **最近 N 轮**（N≈20） | 默认只读最新；历史仅供审计与趋势（"连续 3 轮报磁盘告急"） |
| `handoffs/*.json` | 最近 N 份（N≈20） | 滚动交接只需最新一份；旧份供复盘 |

**不做全历史**——`rounds.log` 已涨到 247KB 且无人读，是反面样本。
趋势类需求由**聚合视图**满足，不靠保留原始记录。

## 5. 人机边界（三档）

现状：红线是**提示词里的中文句子**，是唯一执行机制 —— 权限是建议、越权不可审计、不可测试。

| 档 | 语义 | 实现位置 | 动作举例 |
|---|---|---|---|
| **自主** | 想干就干，事后可审计 | `AGENTRUN` 节点内的工具 | 读台账、跑测试、发简报、写黑板 |
| **授权** | **角色**允许才行；越权=节点失败+告警 | flow 图中的 **GATE 节点**（在 AGENTRUN **之后**、落库之前） | 关单、reopen、cancel execution、删可再生缓存 |
| **人在环** | **人**允许才行；机器只能"报请" | **暂停 → resume**（plaita 已有 `EventNode` + `/api/executions/{eid}/resume`，`test_approval_suspend_then_resume` 已测） | 改并发闸、重启 worker/keeper、动 iOS 模拟器相关、跨仓大动作 |

**授权档的机制**：动作型节点不直接执行，而是**产出 intent**
（`{action, target, reason, evidence}`），由 CODE 节点按能力表 + 路径规则判定。
判定不通过 → 节点失败、写告警、动作不发生、**越权尝试留痕**。

**人在环档的机制**：execution 真的挂起（`status: suspended`），**超时=拒绝（fail-closed），
不是默认允许**。比"发 #2 报请、等下一轮巡检"强一个数量级——后者异步且可能丢。

**待 jeffkit 拍板**：哪些红线升级为 GATE。建议**只升级"违反=不可逆损失"的**：

| 红线 | 建议档位 | 理由 |
|---|---|---|
| iOS 模拟器相关（CoreSimulator / DeviceSupport / Simulator） | **授权（恒定拒绝，与角色无关）** | 不可逆；jeffkit 明确最高优先 |
| 删 `*/target` / 缓存前查 `~/.local/bin` 软链 | **授权**（软链检查结果作为 intent 必填字段） | 10-08 已实证致 VM 全链失败 13 分钟 |
| live run 的 worktree target、`~/.cargo/registry` | **授权（恒定拒绝）** | 不可逆 |
| 重启 worker/keeper/调度服务 | **人在环** | 影响面大，且需与沙箱侧对齐窗口 |
| 改并发闸 / 换模型档 | **人在环** | 全局影响 |
| 不代推他人提交 | 提示词 + 事后审计 | 软纪律，闸门化会让值守寸步难行 |
| DLQ 只记不清 | 提示词 + 事后审计 | 同上 |
| 不动他人 automation | 提示词 + 事后审计 | 同上 |

## 6. 投影（谁是事实来源）

```
   值守 flow ──写──► duty 内核（唯一事实来源）
                        │
                        ├─ 渲染 → GitHub #2/#3（人读、可追溯）
                        ├─ 渲染 → console 值班面板（可选）
                        └─ 快照 → 定期 dump（审计 + 灾备，公网可读）
```

**双向约束**：jeffkit 直接改内核（面板/CLI）时，投影**必须**同步更新，
否则会出现"GitHub 显示与内核不一致"——这正是现在 `.md` 与 `rounds.log` 漂移的老毛病，
换个地方复发。

**投影方向**：内核 → GitHub 由 flow 的 CODE 节点渲染（复用 `github_comment` 节点，
含消毒 + dedup marker + footer）。**保留人工可写 GitHub**：人在 issue 上的发言由
keeper 已有链路回流内核。

## 7. 降级链

| 故障 | 降级 |
|---|---|
| 值守 flow 停摆 | 人工 `launchctl` 拉起后备 zcode 值守（滚动 handoff 仍可冷启动） |
| duty 内核不可读 | 值守轮**只读模式**跑（不动作），告警；不进入"无状态乱动作" |
| GitHub 不可达 | 内核照常写；投影重试；**不阻塞轮次** |
| worker 全灭 | 内核状态仍在，重启后按 cursor 续跑 |

**核心原则**：**正常动作永不依赖单一在线服务**。三个独立故障域
（内核 / GitHub / 执行机）各自降级，不互相拖垮。

## 8. 迁移阶段

| 阶段 | 内容 | 判据（过才进下一阶段） |
|---|---|---|
| **0（本文件）** | 协议 + 四份 Schema + 能力矩阵 + API 草案 | jeffkit 逐条过；schema 能表达现役 playbook 的全部判定 |

| **3 收编主控** | 主控规则化为 `ctrl-tick` flow；人只接升级 | 主控不再持有长会话状态 |

**最小闭环验收标准**（阶段 1 的第一件事）：

> 外部验收方从提 issue 到收到结论，**全程无任何本机文件参与**。
